# Memory Dream Spec

## Purpose

Memory Dream is a thin project-memory harness. It binds a real project directory
to an isolated Typst Zettelkasten wiki managed under `~/.memory-dream`, then
builds that wiki into Markdown artifacts for coding agents.

Memory Dream is not a second ZK implementation. It delegates ZK authoring,
graph checks, note creation, metadata semantics, and link management to
`zk-lsp`.

Version 1 is expected to be a small Python CLI that shells out to `zk-lsp`.

## Core Model

Memory Dream separates four concepts:

```text
real project directory = the work object
~/.memory-dream        = the memory management root
source ZK wiki         = source of truth
Markdown artifact      = agent consumption output
```

The project directory does not need to contain memory files. Project identity is
defined by a registry entry in `~/.memory-dream/dream.toml`.

## Version 1 Requirements

Version 1 must provide a complete local loop:

1. Register the current project without writing generated memory files into it.
2. Create or reuse an isolated ZK wiki for that project under
   `~/.memory-dream`.
3. Delegate ZK checks and wiki setup to `zk-lsp`.
4. Build agent-readable Markdown artifacts from the source wiki.
5. Print the generated project-level memory for agent consumption.

The implementation should favor explicit files and subprocess calls over hidden
services. No daemon is required.

## Project Semantics

A project is a stable mapping from a real project root to one managed memory
workspace.

Project root resolution:

1. `--project-root <path>` when provided.
2. Nearest parent containing `.git`.
3. Current working directory.

The resolved project root is canonicalized before lookup. Commands run from any
subdirectory of a registered project should resolve to the same project entry.

The management root may be overridden with `--dream-root <path>` or a future
environment variable, but the default is always `~/.memory-dream`.

Project IDs are implementation-defined but must be stable and collision
resistant. The recommended default is:

```text
<basename>-<short-hash-of-canonical-root>
```

Example:

```text
memory-dream-8f3a2c
```

## Management Layout

Default management root:

```text
~/.memory-dream/
  dream.toml
  projects/
    <project-id>/
      source/
        include.typ
        index.typ
        link.typ
        note/
      artifact/
        Memory.md
        memory/
      cache/
```

`source/` is the source of truth. `artifact/` is disposable and may be
overwritten by `memory-dream build`. `cache/` is reserved for later query or
indexing features.

## Registry

`~/.memory-dream/dream.toml` records project bindings.

Example:

```toml
version = 1

[[project]]
id = "memory-dream-8f3a2c"
name = "memory-dream"
root = "/Users/pxwg-dogggie/memory-dream"
source = "/Users/pxwg-dogggie/.memory-dream/projects/memory-dream-8f3a2c/source"
artifact = "/Users/pxwg-dogggie/.memory-dream/projects/memory-dream-8f3a2c/artifact"
cache = "/Users/pxwg-dogggie/.memory-dream/projects/memory-dream-8f3a2c/cache"
created_at = "2026-05-22T10:59:00+08:00"
updated_at = "2026-05-22T10:59:00+08:00"
```

The registry is the authority for project-to-memory binding. Source notes remain
the authority for memory content.

Registry invariants:

- `version` is required.
- Each project `id` must be unique.
- Each canonical `root` may appear at most once.
- `source`, `artifact`, and `cache` paths belong to that project's managed
  directory unless an explicit future import command says otherwise.
- A command must fail with a clear message when the current project is not
  registered, except for `init`.

## Source Wiki

`memory-dream init` creates a managed wiki by invoking `zk-lsp init` in the
project's `source/` directory.

The source wiki follows the existing zk-lsp structure:

```text
source/
  include.typ
  index.typ
  link.typ
  note/
    <id>.typ
```

`index.typ` is the project memory entry point. Detailed decision and experience
memories live as ZK cards under `note/`.

Memory Dream should not reimplement ZK CRUD. Future commands such as
`memory-dream new` should wrap `zk-lsp --wiki-root <source> new`.

`zk-lsp` is an external runtime dependency. If it is missing, `init`, `build`
steps that call `zk-lsp`, and `check` must fail with an actionable error.

## Artifact Layout

`memory-dream build` projects source wiki content into:

```text
artifact/
  Memory.md
  memory/
    <id>-<title-slug>.md
```

Mapping rules:

```text
source/index.typ   -> artifact/Memory.md
source/note/*.typ  -> artifact/memory/*.md
```

Artifacts must include a generated marker:

```markdown
<!-- Generated by memory-dream. Edit the source ZK wiki instead. -->
```

Artifacts are not the source of truth and may be overwritten.

Builds should be deterministic for unchanged source input. Before writing new
note artifacts, `build` may replace the whole `artifact/` directory or clean
only files with the generated marker. It must not delete files outside the
managed artifact directory.

## Normalization Rules

Memory Dream does not compile Typst. It normalizes a restricted ZK note format
into agent-readable Markdown.

Required first-version transformations:

```text
#import ...                         drop
#let zk-metadata = toml(bytes(...)) extract TOML metadata
#show: ...                          drop
= Title <2605221059>                # Title
== Section                          ## Section
=== Section                         ### Section
#tag.idea                           move to frontmatter tags
#status_tag(...)                    drop
@2605221059                         resolve to Markdown link when possible
```

The normalizer should treat Typst as a constrained note syntax. It does not
evaluate Typst expressions, templates, or macros. Unknown lines should be
preserved unless they are known source-only scaffolding.

Recommended frontmatter format is TOML frontmatter:

```markdown
+++
id = "2605221059"
title = "Memory Dream"
tags = ["idea"]
source = "note/2605221059.typ"
relation = "active"
checklist-status = "none"
+++
```

The build does not need to produce publishable Markdown. It only needs to
produce readable, low-noise text for agents.

Index files do not need note IDs. `source/index.typ` is normalized into
`artifact/Memory.md` as the project-level memory entry point. Cards under
`source/note/` must have a parseable title line of the form:

```typst
= Title <2605221059>
```

## Link Rules

References use source ZK IDs:

```typst
@2605221059
```

The default artifact link style should be ordinary Markdown:

```markdown
[Memory Dream @2605221059](memory/2605221059-memory-dream.md)
```

If a referenced ID is missing or cannot be resolved, preserve the original
reference:

```markdown
@2605221059
```

This keeps artifacts useful even when the graph is temporarily incomplete.

Artifact note file names should be stable for a given note title and ID:

```text
<id>-<slugified-title>.md
```

If a title changes, the artifact path may change. The source ID remains the
stable identity.

## CLI

First-version commands:

```text
memory-dream init
memory-dream where
memory-dream open
memory-dream status
memory-dream list
memory-dream new
memory-dream edit
memory-dream link
memory-dream build
memory-dream context
memory-dream show
memory-dream check
```

Common options:

```text
--project-root <path>  Resolve or register this project instead of cwd.
--dream-root <path>    Use a non-default management root.
```

### `init`

Registers the current project.

Behavior:

1. Resolve project root.
2. Create `~/.memory-dream` if needed.
3. Allocate `projects/<project-id>/`.
4. Create `source/`, `artifact/`, and `cache/`.
5. Run `zk-lsp init` inside `source/`.
6. Record the binding in `dream.toml`.

`init` must not write memory files into the real project directory.

If the project is already registered, `init` should be idempotent and print the
existing binding.

If `source/` exists but is not empty, `init` should fail unless it already looks
like a zk-lsp wiki for the same registry entry.

### `where`

Prints the resolved project binding:

```text
project:  /path/to/project
id:       memory-dream-8f3a2c
source:   ~/.memory-dream/projects/memory-dream-8f3a2c/source
artifact: ~/.memory-dream/projects/memory-dream-8f3a2c/artifact
```

### `open`

Opens or prints the source wiki path. First version may print the path only.

If `$EDITOR` support is added in version 1, it should be opt-in through a flag
such as `--editor`; the default output should remain script-friendly.

### `status`

Prints project memory state for humans or agents.

Options:

```text
--format text|json
```

Status includes whether artifacts have been built, whether they are stale,
source/artifact paths, note count, linked note count, and unlinked note count.

### `list`

Prints source note IDs and titles.

Options:

```text
--format text|json
```

`list` resolves note IDs from `source/note/*.typ` and should prefer
`zk-lsp note-info <id>` for metadata. It may fall back to parsing the
constrained note heading form if `note-info` is unavailable.

### `new`

Creates a source note by delegating note creation to zk-lsp:

```text
zk-lsp --wiki-root <source> new --json
```

Options:

```text
--title <title>
--id <id>
--kind decision|experience
--content <text>
--link
--build
```

`--link` adds the created note to the project entry point. `--build` explicitly
builds artifacts after creation and optional linking.

`--kind` maps to zk-lsp-supported metadata as a keyword, for example
`keywords = ["decision"]`; memory-dream should not invent metadata fields that
zk-lsp rejects.

If `--id` is omitted, memory-dream allocates the next unused timestamp-like note
ID and passes it to `zk-lsp new --id`, avoiding same-minute collisions with
notes created by `zk-lsp init` or earlier `new` calls.

### `edit`

Prints the source path for an existing note ID:

```text
memory-dream edit <id>
```

With `--editor`, opens the note with `$EDITOR`. The default remains
script-friendly and only prints the path.

### `link`

Links an existing note from `index.typ` so it can enter generated `Memory.md`.

```text
memory-dream link <id>
```

If the ID is already referenced, `link` is idempotent. `--build` explicitly
builds artifacts after linking.

### `build`

Builds Markdown artifacts from the source wiki.

Behavior:

1. Resolve current project binding.
2. Run `zk-lsp --wiki-root <source> generate`.
3. Read `index.typ` and `note/*.typ`.
4. Build an ID-to-title/path map.
5. Normalize files into `artifact/Memory.md` and `artifact/memory/*.md`.

If `zk-lsp generate` fails, `build` should fail before writing artifacts unless
the user explicitly requests a later best-effort mode.

### `context`

Prints AI-consumable Markdown context from existing artifacts.

Behavior:

1. Resolve current project binding.
2. Read `artifact/Memory.md`.
3. Parse `memory/*.md` links in `Memory.md`.
4. Print `Memory.md` plus the referenced note artifacts.
5. Include runtime-resolved project, source, artifact, and note paths so an AI
   can request deeper files without hardcoded machine-specific paths.

By default, `context` does not build artifacts. If artifacts are missing or
stale, the command should ask the user to run `memory-dream build`.

Options:

```text
--max-notes <n>  Limit referenced notes included in the context.
--all            Include every generated note artifact.
```

### `show`

Prints `artifact/Memory.md`. If artifacts are missing, the command should ask
the user to run `memory-dream build` or optionally support `--build`.

### `check`

Delegates graph integrity checks to zk-lsp:

```text
zk-lsp --wiki-root <source> check
```

Memory Dream may add registry and artifact checks later.

Exit status should match the delegated `zk-lsp check` result.

## Codex Skills

The repository distributes Codex skills under `skills/`:

```text
skills/memory-dream-coding
skills/memory-dream-curator
```

Install them into a Codex skills directory with:

```bash
mkdir -p "${CODEX_HOME:-$HOME/.codex}/skills"
rsync -a skills/memory-dream-coding "${CODEX_HOME:-$HOME/.codex}/skills/"
rsync -a skills/memory-dream-curator "${CODEX_HOME:-$HOME/.codex}/skills/"
```

`memory-dream-coding` is for normal coding sessions: load project context,
keep artifacts current, and record lightweight decision or experience notes.

`memory-dream-curator` is for periodic consolidation: review notes, link
durable memories into `Memory.md`, rebuild artifacts, and verify `context`.

## Error Handling

Commands should distinguish these common failures:

- unregistered project
- missing `zk-lsp`
- invalid or unreadable registry
- source wiki missing expected files
- invalid note header
- unresolved reference reported by `zk-lsp check`

Errors should include the project root and source path when relevant.

## Non-Goals For Version 1

Version 1 does not include:

- SQL database storage.
- Embedding or vector search.
- Provider integration for Alma, Codex, or Claude memories.
- Query APIs beyond `context` and `show`.
- Bidirectional sync from Markdown artifact back to Typst source.
- Writing generated memory files into the real project root.
- Reimplementing zk-lsp graph semantics.
- Modifying `zk-lsp export`.

## Future Extensions

Likely follow-up features:

- `memory-dream dream` for agent-assisted project memory synthesis.
- `memory-dream query` using artifact text, backlinks, and optional cache.
- Optional mirror of artifacts into a project directory.
- `note-info --all` or graph JSON integration if zk-lsp exposes it later.
